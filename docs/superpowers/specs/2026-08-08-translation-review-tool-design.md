# 翻译译名校对工具设计

日期：2026-08-08  
状态：已确认，待编写实现计划

## 1. 目标

为本项目增加一个只在本机运行的译名校对台，用于快速浏览和修改卡牌中文名。

页面需要：

- 按现有翻译批次分页，例如英雄、通用、装备、战士、守护者等；
- 展示英文卡名、现译名、更新译名三个核心字段；
- 鼠标悬停英文卡名时显示卡图；
- 同一基础卡名的红、黄、蓝 pitch 版本合并为一行；
- 允许用户反复修改任意译名；
- 点击提交后生成项目内的待处理 JSON，不直接改正式翻译源。

工具不编辑卡牌正文，不处理术语表，也不使用 `status` 作为界面标签、筛选条件或修改依据。

## 2. 现有项目约束

正式翻译源位于 `data/translations/*.json`，每个文件对应一个确定性翻译批次。卡牌的 pitch 版本使用基础 slug 加 `__1`、`__2`、`__3` 后缀区分。

英文卡牌信息使用 `data/cards.en.json`。其中的 `printings[].image_url` 可作为卡图预览地址，`source` 可作为卡牌详情页的备用链接。

现有构建器 `scripts/build-card-data.mjs` 会将批次文件构建为 `dist/data/`。翻译校对台不应读取或修改发布产物作为源数据。

## 3. 架构

新增一个无第三方运行时依赖的本地 Node 服务：

```text
tools/translation-review/
  index.html
  app.js
  styles.css

scripts/translation-review-server.mjs
data/review-submissions/
  pending/
  processed/
```

服务默认监听 `127.0.0.1:4174`，支持通过命令行参数或 `PORT` 环境变量覆盖端口。服务同时负责：

1. 提供静态前端文件；
2. 读取翻译源和英文卡库；
3. 提供分页、搜索和批次接口；
4. 校验提交请求；
5. 将提交内容写入 `pending/`。

建议在 `probe/package.json` 增加：

```json
{
  "scripts": {
    "review": "node ../scripts/translation-review-server.mjs"
  }
}
```

启动方式为 `cd probe && npm run review`。

服务只绑定回环地址，不提供远程访问，也不需要账号系统。静态路径和 API 参数必须经过路径安全校验，不能让请求读取项目外部文件。

## 4. 数据聚合规则

服务读取批次文件后，以去除 `__1`、`__2`、`__3` 后缀的基础 slug 分组。每个基础 slug 对应前端的一行；底层的每个 pitch 条目仍然独立保留。

每行至少包含：

- `card_id`：基础 slug；
- `batch`：所属翻译文件名；
- `name_en`：英文卡名；
- `image_url`：第一张可用印刷图；
- `source`：卡牌详情页；
- `variants`：每个原始条目的 key、pitch、现有 `name_zh`、正文和数值的只读摘要。

现译名展示规则：

- 所有版本译名相同：直接显示一个译名；
- 版本译名不同：显示警告，并按 pitch 列出各版本旧译名；
- 不合并正文、费用、力量、防御或其它版本字段。

用户输入一个新译名后，提交时将其应用于该基础 slug 下所有现有 pitch 条目的 `name_zh`。不存在的 pitch 不会被凭空创建。

`status` 字段既不返回为筛选依据，也不在界面展示；正式源文件中的原值在未来应用修改时保持不变。

## 5. HTTP 接口

### `GET /api/batches`

返回 `data/translations/` 下的 JSON 批次列表和每个批次的卡牌行数量。批次名称来自实际文件名，避免前端维护一份可能过期的分类表。

### `GET /api/cards`

支持参数：

- `batch`：批次名；
- `q`：英文卡名或现译名搜索词；
- `page`：从 1 开始；
- `page_size`：服务端限制在合理范围内。

返回当前页行数据、总行数、当前页码和页大小。搜索与分页在服务端完成，避免首次加载所有卡牌数据。

### `POST /api/submissions`

请求体只允许包含发生修改的行：

```json
{
  "changes": [
    {
      "card_id": "a_bit_off_the_side",
      "batch": "t3-warrior",
      "name_en": "A Bit off the Side",
      "new_name_zh": "偏锋一击",
      "variants": [
        { "key": "a_bit_off_the_side__1", "current_name_zh": "偏门一击" },
        { "key": "a_bit_off_the_side__2", "current_name_zh": "偏门一击" },
        { "key": "a_bit_off_the_side__3", "current_name_zh": "偏门一击" }
      ]
    }
  ]
}
```

服务端校验基础 slug、批次、变体 key 和非空的新译名。通过校验后为整次提交生成唯一文件：

```text
data/review-submissions/pending/submission-<timestamp>-<id>.json
```

文件另存 `schema_version`、`submission_id` 和 `submitted_at`，便于后续校验和追踪。前端提交成功后显示文件名与条目数量。

## 6. 应用提交

后续由 Agent 读取 `pending/` 中的提交，并通过专用应用流程更新翻译源。应用流程必须先完成整份提交的校验，再写文件：

1. 确认每个批次文件存在；
2. 确认每个变体 key 仍存在且仍在声明的批次；
3. 确认每个变体的当前 `name_zh` 与提交快照一致；
4. 在内存中只替换对应条目的 `name_zh`；
5. 原子写回受影响的批次文件；
6. 运行 `npm run build:data` 和 `npm test`；
7. 成功后将提交文件移到 `processed/`，并记录处理时间。

如果任一条目发生冲突，整份提交不应用、不部分写回，原文件留在 `pending/`，并报告具体卡名、变体和当前值。这样可以避免页面打开时间较长时覆盖其他人的手工修改。

应用过程不会修改 `status`，也不会修改正文或任何 pitch 数值。

## 7. 页面交互

页面顶部包含标题、搜索框和批次分页。主体为三列表格：英文卡名、现译名、更新译名。

- 英文卡名悬停显示卡图；
- 卡图使用固定定位的预览浮层，避免撑开表格；
- 卡图加载失败时显示卡名和来源链接；
- 更新译名输入框默认为空；
- 输入内容在分页和批次切换期间保留；
- 空输入或与现译名相同的行不会提交；
- 页面底部固定显示当前修改数量和提交按钮；
- 提交失败时保留所有输入，允许重试。

第一版不加入正文编辑、批量自动翻译、用户登录、远程后端、多人协作或自动推送。

## 8. 测试范围

新增 Node 测试覆盖：

- 批次文件加载和基础 slug 分组；
- 同名 pitch 版本聚合为一行；
- 版本译名不一致时的警告数据；
- 提交只包含有变化的译名；
- 提交文件写入 `pending/`；
- 非法 key、批次、空译名和越权路径被拒绝；
- 应用提交只修改 `name_zh`；
- 不同 pitch 的正文和数值保持原值；
- 旧值快照冲突导致整份提交不应用；
- 成功应用后移动到 `processed/`。

现有翻译目录约束测试和数据构建测试继续作为回归测试，不因工具引入新的 status 值或新的翻译源文件格式。

## 9. 验收标准

完成后，用户可以：

1. 执行 `cd probe && npm run review` 打开本地工具；
2. 在分页中找到任意卡牌；
3. 悬停英文名看到卡图；
4. 输入新译名并提交；
5. 在 `data/review-submissions/pending/` 看到提交文件；
6. 让 Agent 读取并应用提交；
7. 确认对应批次的所有 pitch 条目译名同步更新；
8. 确认正文和数值没有变化；
9. 确认构建产物和现有测试通过。
